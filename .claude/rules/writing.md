# 執筆ルール

## 1. 文体

### トーン

- **本文**: 落ち着いた敬体で、直接的・説明的に書く。過度に個人的な語りかけ（「率直に言うと」等）や、比喩・修辞で飾るエッセイ調の冗長な語りは避ける
  - 比喩を多用しない。「登る道のり」「地図を広げる」「いま立っている場所」のような言い換えより、事実をそのまま述べる
  - 情緒的な前置き・修辞を避ける（「〜という経験はないでしょうか」「まさにそのために」「安心して読み進めてください」等）。課題や意義は一文で端的に示す
  - 字数は内容の厚み（具体例・コード・図・概念の掘り下げ）で満たす。字数の目安に届かせるための冗長な言い換えや装飾はしない
- **現場での考え方**（一人称の実体験を語る枠。`!!! quote "現場での考え方"` の admonition で表す）: 一人称（「自分は」「私が」）で、具体的な失敗談・設計判断の裏話・実務のあるあるを語る。本文より口語的でよいが、「率直に言うと」「正直に言うと」等の前置きや読者を試す表現は避ける。分量は **数文程度** に抑える（具体的な経験ひとつと、そこからの学びで十分。長い物語にしない）。**毎セクション必須ではない**。置くと効果的なセクションだけに置き、全セクションへ同型で反復しない（「症状の一般化 → 失敗 → 教訓」の型を毎回くり返さない）

### 用語・表記

- 敬体（です・ます調）で統一。読者を指す語は「あなた」「学習者」を用い、特定の制度名・組織名（受講区分・所属組織名など）は本文で使わない
- 本文は学習者に向ける。事業・運営側の文脈は本文に持ち込まない: 特定の顧客企業名・受講企業名、助成金・契約・料金、アフターサポートや成果指標の約束、評価・採点、estra の社内事情。必要な場合は一般化して書く（例: 「あなたの会社」「実務の現場」）
- ダッシュ記号（`——`、`—`、`–`）は使わない
- Claude Code の用語は参考資料の表記に従う。範囲外の内容は WebSearch / WebFetch で裏付ける
- 時間経過で変わる情報は最新情報を取得し「○○時点」と日付を明記
- 教材が前提とするバージョンと、読者が現場で遭遇しうるバージョンに差がある場合は、本文は前提バージョンで書き、差分は `!!! tip` / `!!! note` の短いコラムで補足する（本文を散らかさない）
- 外部ソースを参照する場合は出典を明記する
- `**太字**` は語句・キーフレーズに限定する。文全体を太字にしない。admonition のタイトル（`!!! note "補足"` の「補足」）が見出しの役割を果たすので、ボックス内の本文を丸ごと太字にしない（❌ ボックス内全文を太字 → ✅ キーフレーズだけ太字）
- Markdown の `**text**` は閉じ `**` 直後にスペースなしで日本語が続くと適用されない。`**○○** の場合` のようにスペースを入れる。全角括弧 `（` も同様: `**○○**（補足）` → `**○○** （補足）`

| セクション | 教材本文ではカタカナ表記。内部ドキュメントでは英語 |
| Claude Code | 製品名。英字のまま（カタカナにしない） |

### コラム（admonition）と絵文字

見出し（`##`／`###`）には絵文字を付けない。補足・注意・実体験などのコラムは、装飾絵文字ではなく MkDocs Material の admonition（色付きの囲みボックス）で表す。本文・コラム内でも装飾絵文字（🚀🎯✨💡 等）は撒かない。

| 用途 | 記法 |
|---|---|
| 補足・ノート・定義 | `!!! note "補足"`（前提知識は `!!! note "前提知識"`） |
| ヒント・TIP | `!!! tip "ヒント"` |
| 注意 | `!!! warning "注意"` |
| よくあるエラー（コード付き） | `!!! warning "よくあるエラー"` |
| 重要ポイント | `!!! info "ポイント"` |
| 現場での考え方（一人称の実体験） | `!!! quote "現場での考え方"` |
| 確認（やってみよう／Step 末尾） | `!!! success "確認"` |

- admonition 内の本文・リスト・コードは **4 スペース字下げ**（字下げを忘れるとボックスにならない）。
- 折りたたみは `???`（pymdownx.details）、または `<details>`。
- コラムは要点だけに使い、乱発しない（目安: 1 セクションで合計 3〜4 個まで）。同じ種類を連続で並べない。
- キー名や記号そのものを示す表記（`⌘`・`⊞`・チェックボックス `- [ ]` 等）は内容なので対象外。

### OS 別の記載（コンテンツタブ）

macOS と Windows で操作が分かれる箇所は、両方を本文に並べて読者に探させるのではなく、MkDocs Material のコンテンツタブで OS ごとに切り替えられるようにする（`pymdownx.tabbed` で実装。GitHub Pages で有効済み）。読者は自分の OS のタブだけを読めばよい。

```markdown
=== "macOS"
    （macOS 向けの手順）

=== "Windows"
    （Windows 向けの手順）
```

- タブの中身は **4 スペース字下げ** （admonition と同じ。字下げを忘れるとタブにならない）。各タブブロックの前後には空行を置く。
- ラベルは `"macOS"` `"Windows"` で固定し、表記ゆれ（「Mac」等）を使わない。`content.tabs.link` と `navigation.instant` が有効なため、同じラベルのタブはサイト全体で連動し、読者が一度 Windows を選ぶとページを移動しても Windows のまま表示される。ラベルが一致しないと連動しないので、綴り・大文字小文字まで揃える。
- 並び順は macOS → Windows で統一する（先頭のタブが既定表示）。Linux に触れる必要がある箇所のみ3つ目に `=== "Linux"` を足す。
- タブにするのは、OS で手順が分岐する **まとまった操作ブロック** だけにする（ターミナルの開き方、設定画面の手順など）。`/` と `\` 、`%` と `>` のような短い差や、「OS でこう違う」という比較・解説そのものが目的の箇所は、本文に併記するインラインのままでよい（タブにすると過剰になる）。
- タブは原則トップレベルに置く。admonition の中に入れると字下げが深くなり崩れやすいので避ける。

## 2. 構造

### Section の種類

| 種類 | 内容 |
|---|---|
| **概念** | 意義・仕組み・使い方を解説 |
| **ハンズオン** | 概念で学んだ機能を実践。冒頭に概念 Section への逆リンク |
| **混合** | 概念を学びながらすぐに手を動かす |

### 見出しの設計

**Why → What → How**（抽象→具体）の流れで組む。見出しに絵文字を付けず、プレーンな名詞句・トピック名にする。「なぜ〜のか」の疑問形より名詞句（「〜の理由」）を優先し、無生物の擬人化（「AI が〜を好む」等）を見出しに持ち込まない。

### テンプレート

全 Section 共通の骨格に、種類ごとの差分を組み合わせる。見出しに絵文字は付けない。コラムは admonition で表す。

```markdown
# [セクション番号] セクションタイトル

<!-- 前提がある場合: !!! note "前提知識" を挿入 -->
<!-- 概念（グループ先頭）の場合: グループ全体像を挿入 -->
<!-- ハンズオンの場合: !!! note "このハンズオンで使う機能" を挿入 -->

## このセクションで学ぶこと

- 学習目標1
- 学習目標2

[Section の狙いを1文で（見出しの丸写し列挙はしない）]

---

## 導入: [課題・痛みから入る見出し]

<!-- 効果的なセクションのみ: 一人称の実体験を下記で添える -->
!!! quote "現場での考え方"
    [一人称の実体験を数文で]

---

<!-- 本文: 種類ごとに異なる（「種類ごとの差分」を参照） -->

---

## まとめ

- ポイント1
- ポイント2

---

次のセクションでは、[次の内容への接続]。
```

**次セクションへの接続**:
- プレーンテキストで記述する（Markdown リンクやカギ括弧は使わない）
- **次セクションへの接続文** は、OUTLINE.md の次セクションのゴールに含まれるキーワードを漏れなく含める。ただし毎回同じ言い回し（「次のセクションでは、〜を扱います。〜を押さえ、〜を理解します。」）を避け、運びを変える
- **Chapter 最終セクション**: Chapter の学びの振り返り + 次の Chapter への橋渡し
- **Part 最終セクション**: 上記に加え、Part 全体の振り返り + 次の Part への橋渡し
- **教材全体の最終セクション**: 教材全体の締め括り文を記述する（学んだことの振り返り + 次のステップへの示唆）

### 種類ごとの差分

**概念**:

- 本文は `## 見出し` で構成する
- 2層以上の場合、親グループの最初の Section のみ、タイトル直後にグループ全体像を含める。種類が混合でもグループ先頭であれば同様に含める。グループ全体像は `##` 見出しを使わず、タイトル直後に直接記述する。構成: ① 概要文（1-2文）② セクション一覧テーブル（セクション / テーマ / 種類）③ `**この Chapter の進め方**: [学習の流れ]`（絵文字なし）
- 概念 Section（特に Part2〜5）は、本文の後・`## まとめ` の前に、その Section で学んだことを実際に手で確かめる小さな実践 `## やってみよう` を置く（OUTLINE 種類方針。座学が続くのを防ぐ）。**`/write` の一回の執筆で、本文と一緒に「やってみよう」まで書く**（本文だけ先に書いて別パスで後追記する運用はとらない）。手を動かす意味が薄い Section では省いてよい。「（任意）」とは書かず、受講者が手を動かす前提で書く
- やってみようの手順は **ターミナル未経験の非エンジニア** が迷わない粒度で書く: ターミナルの開き方・キー操作（⌘+スペース／⊞+X 等）・画面に表示されるもの・打つ文字・押すキー・返ってくる結果・OS 差を省略しない（公式「新規ユーザー向けターミナルガイド」の粒度が基準。「Spotlight で開く」のように前提知識を要する省略をしない）。各ステップは観察できる達成状態で締め、末尾に `!!! success "確認"` のコラムを置く。ターミナルの開き方など繰り返す操作は、初出 Section で詳述し以降は初出への参照＋要点（キー操作）の再掲にとどめる。書き換えを伴う場合は末尾でクリーンアップする（「実践パートの品質」参照）

**ハンズオン**:

- タイトル直後に `!!! note "このハンズオンで使う機能"` で機能名（[セクション名] で学習）を挿入
- 導入の後に `## [作業名]前の確認`（チェックリスト形式）を挿入
- 本文は `## 実践: [タイトル]` の中に `### Step N: [タイトル]` の連番で構成する
- 本文の後、まとめの前に `## 完成チェックリスト` を挿入
- 長いコードは `<details>` で折りたたむ

**混合**:

- 本文の前半は `## 見出し`（概念解説）で構成する
- 本文の後半は `## 実践: [タイトル]` の中に `### Step N: [タイトル]` の連番で構成する
- 本文の後、まとめの前に `## 完成チェックリスト` を挿入

**エラーフォーマットの使い分け**:
- エラーメッセージ（コードブロック）を伴う場合 → `!!! warning "よくあるエラー"` の admonition（下記テンプレート）
- エラーメッセージなしの一般的な注意 → `!!! warning "注意"` で記述

````markdown
!!! warning "よくあるエラー"
    [概要]

    ```text
    [エラーメッセージ例]
    ```

    **原因**: [なぜ発生するか]

    **対処法**: [解決手順]
````

（admonition 内は 4 スペース字下げ。コードフェンスもボックス内に字下げして置く）

## 3. コンテンツ

### コードの見せ方

- コードを含む場合、コードブロック上部にファイルパスをコメントで明示する。コメント構文は言語タグに合わせる:
  - `java` / `typescript` / `javascript` / `php` / `jsonc`: `// filepath`
  - `tsx` / `jsx`: `{/* filepath */}`
  - `yaml` / `properties` / `dockerfile` / `bash` / `toml`: `# filepath`
  - `css`: `/* filepath */`
  - `xml`: `<!-- filepath -->`
  - `sql`: `-- filepath`
  - `<?php` で始まる PHP ファイルなど、先頭に固定行があるファイルは、パスのコメントをその固定行の **次の行** に置く（固定行より前に置くと、そのまま貼り付けたときにコードの外側のテキストとなり壊れるため）
- コードブロックには必ず言語を指定する。非コードコンテンツ（ディレクトリツリー、コマンド出力等）には `text` を使用する
- diff 表示は使わない（テキストで説明し変更後のコードを示す）
- **参考資料のコードを引用する場合は正確性を最優先する**。コードを簡略化して掲載する場合は、コードブロックの直前に「以下は主要部分の抜粋です」と明記し、省略した重要な処理を本文で補足する。ファイルパス・変数名・設定値は実ファイルと完全に一致させる
- 図（処理フロー・リレーション・ER 図等）を Mermaid で描く場合、コードブロックの言語タグは `mermaid`

### 解説の深さ

- OUTLINE.md に前提（`前提:` フィールド）が記載されている場合、`## このセクションで学ぶこと` の前に `!!! note "前提知識"` を置き「このセクションは○○の内容を前提としています。」と明記する
- 前提知識（概念）は概念の再入門を省略する。ただし Claude Code での具体的な実現（記法・作法・差異）は省略せず解説する。既習との差異・組み合わせ時の注意点は特に丁寧に
- Claude Code 固有の概念は初出時に丁寧に解説し、2回目以降は初出 Section への参照
- 同じ概念を別の箇所で繰り返さない
- 導入は「これがないと何が困るか」（課題）から入る
- 処理の流れ・サイクル・リレーション・ER 図は Mermaid で視覚化する（MkDocs Material / GitHub Pages で描画される。コードブロックの言語タグは `mermaid`）
- 未説明の用語をツリーやリストに含める場合は、簡潔なコメントか後続セクションへの参照を付ける
- つまずきポイントを先回りする（`!!! warning` で説明）
- 先の Section で扱う内容は「今は概要だけ把握すれば十分です」と明記する
- **概念 Section にコマンドやコードを載せる場合**、本文中のそれは「読んで理解するための例であり、読みながら打つ必要はない」ことを学習者に明示する。`## このセクションで学ぶこと` の直後に `!!! note` で一言添える。`## やってみよう` がある Section では「本文のコマンド・コードは仕組みを理解するための例です。実際に手を動かすのは末尾の『やってみよう』です（本格的な操作・開発は該当ハンズオン／Part6）」の趣旨に、やってみようが無い Section では「実際に動かす（書く）のは○○（該当ハンズオン／総合ハンズオン）です」の趣旨にする。混合・ハンズオン Section は全体で手を動かすため、この断りは不要
- 画像（概念図）の扱いは `/illustrate` を使うかで分かれる。**使う場合**: 執筆段階では挿入せず、挿入位置も `/illustrate` が計画するため TODO プレースホルダーも置かない（密度方針は criteria.md「0. 画像の密度方針」: 各概念 Section に 1 枚）。**使わない場合**: 初回リリースでは画像を含めず `<!-- TODO: 画像追加 - ○○の画面 -->` でプレースホルダーを残す（TODO コメントの画面名は実際の表示と一致させる。例: 自動ログインされる画面に「ログイン画面」と書かない）
- Section あたりの目安文字数: 4,000 文字程度（必須の下限ではなく、あくまで目安。概念 Section は Why → What → How を丁寧に書くと自然にこの程度を超えることが多い。内容が過不足なく簡潔にまとまっていれば目安を下回ってよい。字数を満たすための加筆はせず、冗長を避けて概念理解を優先する）

### 実践パートの品質

実践・ハンズオンを含む Section では、以下を守る:

- **学習者が直接打つ操作の再現性は保証する**: 学習者自身が実行するコマンド・Git 操作・環境構築の手順は、記載どおりで期待する結果になることを実際の動作から確認する。特に Git 操作（`git checkout`, `git restore`, `git reset` 等）は、ステージ状態・ブランチ状態を正確に追跡し、クリーンアップ手順まで含める（AI が生成するコード・出力の再現性は保証しない。その扱いは次節）
- **前提状態を明示する**: 各ステップの実行前に必要な状態（コンテナ起動済み、特定ブランチにいる等）を、始める前のチェックリスト（`## [作業名]前の確認`）で示す
- **副作用のクリーンアップ**: 実践で作成したブランチ・コミット・ファイル変更は、セクション末尾で元に戻す手順を必ず含める

### ハンズオンの書き方（AI に開発・作業を委任する前提）

本カリキュラムのハンズオンは、学習者が手でコードを書くのではなく、AI（Claude Code）に開発・作業を委任して進める。AI の出力（コード・対話・エラー文）は毎回異なるため、プログラミング教材のように「コードを上から順にコピペすれば記載どおりにビルド／実行が通る」ことは **保証しない・目指さない**。代わりに、**意図（What）・判断・検証・成果物の“形”** を書く。次を守る。

**固定する層と流動する層を分ける**

- **固定（そのまま書く）**: 学習者自身が打つコマンド（環境構築・`npx`・`wrangler`・`npm run dev`・デプロイ等）、作業場所（カレントディレクトリ）、cc-sdd などが生む成果物の“形”（どんなファイル・段が生まれるか）、動作確認の手順、画面で行う操作。ここは決定的なので正確に書く
- **流動（そのまま載せない）**: Claude が生成するコード、対話の細部、エラーの文面。これらは「例（あなたのものは異なる）」と明示してのみ載せる

**各ステップのゴールは「観察できる達成状態」で書く**

- コードや出力の一致ではなく、「○○すると △△ が返る／画面に □□ が表示される／公開 URL が開ける」という観察できる状態で合否を定義する。`完成チェックリスト` も、コード一致ではなく観察できる達成状態の列挙にする

**AI 生成物を載せるときは必ず“例示”と明示する**

- コードや AI の出力を載せる場合は「これは Claude が出す一例で、あなたのものは違ってよい。大事なのは ○○ できること」と添える。実挙動との一致を求めるのは、学習者が直接打つコマンドの結果など **決定的な部分に限る**

**詰まりは“症状ベース”で先回りする**

- 固定のエラー文を網羅するのではなく、「想定どおり動かないときは、期待した結果と実際の様子を Claude に伝えて直してもらう」という委任のメタスキルで書く（必要条件 C-2）。`!!! warning` コラムも「この種のつまずきが起きうる → こう伝えて直す」の形にする

**足場（環境・配置・コマンド）は省略せず正確に書く**

- 環境構築・アカウント作成・`cd`・実行コマンド・デプロイ手順など、学習者が直接実行する決定的な部分は省略しない。各コマンドの **実行場所（カレントディレクトリ）を毎回曖昧にしない**。OS 差（コマンド名・パス区切り等）は初出で一度示し「以降も同様」と添える
- ファイルの作成・編集は Claude Code に委ねるのが基本なので、`touch` で各ファイルを作らせる指示は不要。学習者が自分で用意・確認するファイル（環境変数・設定値・アカウント情報など）がある場合のみ、どこに何を置くかを明示する

**cc-sdd を再現性の背骨にする**

- コードは毎回違っても、cc-sdd の「要件 → 設計 → タスク → 実装」という過程と生成物の“形”は揃う。教えるのは過程、確認するのは成果物の形と完成条件。これにより、出力が非決定的でも学習者が同じ地図の上を歩ける

**ツール・フレームワークの挙動は裏取りしてから断定する**

- 成否を分ける箇所（cc-sdd のコマンド名、Cloudflare／Next.js の対象バージョンでの挙動、無料枠の制約など）は、公式ドキュメント／実機で確認してから書く。版変動が速いので「○○時点」を明記する

**コードを書かない設計 Section の表現**

- 設計だけで成果物（ファイル）が生まれない Section では、「完成チェックリスト」「成果物が揃っている」といった表現を避け、「設計を説明できる / 決められた」など **理解・意思決定** として書く。冒頭の `!!! note` も「使う機能」ではなく「活かす概念」等、実態に合わせる
