# 3-1-6 出力の検証と軌道修正

!!! note "前提知識"
    このセクションは 3-1-5「中断・巻き戻し・再開」と 1-3-4「構造化とアウトカムから決める完成条件」の内容を前提としています。

## このセクションで学ぶこと

- AI の出力を、完成条件と一項目ずつ照らして確かめること
- 数字・固有名詞・出典は、一次情報で裏取りすること
- ずれたら軌道修正を指示し、タスクを小さく刻んで一段ずつ確かめる検証ゲート

立派に見える出力を鵜呑みにせず、完成条件で確かめて狙いに収束させる工程を押さえます。

!!! note "補足"
    本文の進め方は、検証の考え方を理解するための説明です。実際にこの検証を回して記事を1本仕上げるのは、Chapter 3-5 の記事づくり（3-5-1）です。AI に自動テストを書かせて回すのは Part6 で扱います。

---

## 導入: 立派に見える出力ほど、確かめる

1-3-2 と 2-5-2 で、生成AI が「誤りを自信ありげに返す」こと、もっともらしいのに中身が違う出力を自然に作れてしまうことを見ました。これは仕組み上避けられない癖でした。

だから、受け取る側が確かめます。出てきたものが立派に見えるほど、見た目に引っぱられて確認を省きたくなりますが、そこが落とし穴です。AI に任せて成果物を仕上げるには、出力を検証して、ずれていれば直し、狙いに収束させる工程が欠かせません。その確かめ方を、ここで身につけます。

---

## 完成条件と一つずつ照らす

確かめるときの拠りどころが、1-3-4 でアウトカムから逆算して決めた **完成条件** です。「なんとなく良さそう」「立派に見える」という曖昧な感想ではなく、点検できる条件と照らして、一項目ずつ「できているか」を見ます。

1-3-4 では、ある記事の完成条件を次のように決めました。

- 想定した初心者がつまずく一点が、具体例つきで解説されている
- どこかで読んだ一般論ではなく、実務に踏み込んだ中身がある
- 読み終えた読者が、次に何をすればよいか分かる
- 2000字程度で、専門用語にはひとこと説明がある

出てきた記事を、この4項目に一つずつ当てて確かめます。「具体例はあるか」「一般論で終わっていないか」「次の一歩が示されているか」「字数と用語説明はどうか」。曖昧な印象で全体をまとめて評価するのではなく、点検できる条件に分けて見るからこそ、どこが足りないかが具体的に分かります。完成条件を先に決めておく意味が、この検証の段で効いてきます。

## 事実と出典は一次情報で裏取りする

完成条件との照合に加えて、出力に含まれる事実は別に確かめます。2-5-2 で見たハルシネーション（もっともらしい誤り）への対策です。

とくに **数字・固有名詞・出典** は、そのまま信じてはいけません。AI は「出典がありそうな形」を作るのも得意で、実在しない書名やページ数を、それらしく返すことがあります。これらは、AI に調べさせたうえで、公式の情報や元のデータ（一次情報）にあたって確かめます。

!!! warning "注意"
    AI が示した出典や数字を、確認せずに資料へ載せるのは避けてください。「その主張の根拠となる一次情報を示して」と調べさせ、示された出典を自分で開いて、本当にその内容が書かれているかを確かめます。出典そのものが実在しない、あるいは内容が違う、ということが起こりえます。調べさせること（リサーチ）と、裏を取ること（一次情報の確認）は、セットで行います。

## ずれたら軌道修正を指示する

照合や裏取りで、狙いとのずれが見つかったら、軌道修正を指示します。このとき効くのが、**期待した結果と、実際にどうだったかを具体的に伝える** ことです。

「なんか違う」「もっと良くして」では、AI は何をどう直せばよいか分からず、解釈で埋めてまた的を外します。「○○の項目について、一般論で終わっていて具体例がない。実務での具体例を1つ加えてほしい」のように、どの完成条件のどこがどうずれているかを具体的に伝えると、修正が狙いに向かいます。指示が具体的であるほど、必要な修正は少なくて済みます。

!!! info "ポイント"
    同じ箇所を何度も直してもらっても収束しないときは、やり取りを重ねるより、いったん仕切り直すほうが速いことがあります。それまでの長いやり取りには、うまくいかなかった試みが積もっていて、かえって AI を迷わせるからです。これまでに分かったことを踏まえた具体的な指示を、整理した文脈で出し直すと、収束が早まります。やり取りが膨らんだときに文脈を整える手段は、次の Chapter 3-2 で扱います。

## 検証ゲート: 小さく刻んで一段ずつ確かめる

ここまでの「完成条件と照らす」「裏を取る」「ずれたら直す」を、いつ行うかが大切です。大きく一気に作らせてから最後にまとめて確かめると、ずれが累積していて、どこから直せばよいか分からなくなります。

そこで、大きな仕事を小さく刻み、一段ごとに完成条件と照らして、合格してから次へ進みます。この一段ごとの確認を **検証ゲート** と呼びます。1-3-4 で構造化（小さな単位に分ける）を学びましたが、その分けた一つひとつの区切りに、確認の関所を置くイメージです。一段ずつ確かめながら進めば、ずれは小さいうちに見つかり、立て直しも軽くて済みます。

ここで、2-2-3 で学んだ自動テストと区別しておきます。自動テストは、ソフトウェアが期待どおり動くかを機械が自動で確かめる仕組みでした。このセクションで扱う検証ゲートは、それとは別の、**人が完成条件に照らして確かめる** 検証です。記事の内容が狙いに合っているか、といった判断は、人が完成条件で見ます（AI に自動テストを書かせて回すのは、コードを扱う Part6 で実践します）。

!!! tip "ヒント"
    人が確かめるとはいえ、AI に **検証の手段** を出させると、確認がぐっと楽になります。Claude Code のベストプラクティスでも、AI に合否を返せるもの（テストの結果・スクリプトの実行結果・画面のスクリーンショットなど）を与えると、AI 自身がそれで確かめながら反復できる、とされています（2026年6月時点）。「成功した」と主張させるだけでなく、根拠（実行した結果やスクリーンショット）を示させると、こちらの確認も速くなります。

この「完成条件を先に決めて、小さく刻んで一段ずつ照らす」進め方は、本研修の背骨です。Part4 では、これを大きな仕事を破綻なく仕上げる仕様駆動（4-2）として体系立てて扱います。いまは、基本操作の一部として、出力を検証ゲートで確かめながら進める型を押さえてください。

## まとめ

- 立派に見える出力ほど鵜呑みにせず、1-3-4 の完成条件と一項目ずつ照らして確かめる
- 数字・固有名詞・出典は、AI に調べさせたうえで一次情報にあたって裏を取る（2-5-2 のハルシネーション対策）
- ずれたら、期待した結果と実際の様子を具体的に伝えて直してもらう。指示が具体的なほど修正は少なくて済む
- 大きく一気に作らせず、小さく刻んで一段ごとに完成条件と照らしてから次へ進む（検証ゲート）。AI に合否を返せる検証手段を出させると確かめやすい
- ここで扱うのは人が完成条件で確かめる検証。機械が自動で確かめる自動テスト（2-2-3）を AI に書かせて回すのは Part6

---

これで Chapter 3-1 は終わりです。この Chapter では、Claude Code を動かす一連の基本操作を扱いました。依頼を投げると AI が自分でファイルを読み・調べ・編集まで進めること（3-1-1）、ファイルの編集と差分での確認（3-1-2）、モデルや努力レベル・コストの見方（3-1-3）、権限モードと Plan モードで自律度を選ぶこと（3-1-4）、実行を止める・巻き戻す・再開すること（3-1-5）、そして出力を完成条件で検証して軌道修正すること（本セクション）。安全に実行し、出力を確かめて狙いに収束させるところまでが、基本操作としてつながりました。

これらの操作には、一つ共通の土台があります。AI が一度に保持できる文脈の量です。やり取りが長くなって文脈が膨らむと、AI は前の指示を取りこぼしたり、精度が落ちたりします。次の Chapter 3-2 では、この文脈を **コンテキスト** として正面から扱います。最初のセクション 3-2-1 では、AI が一度に読める範囲（コンテキストウィンドウ）には限りがあり、作業を続けると埋まっていくこと、文脈が膨らむと精度・速度・コストに影響することを押さえます。何を入れて何を入れないかが成果を左右する、Claude Code 活用の要を理解していきます。
