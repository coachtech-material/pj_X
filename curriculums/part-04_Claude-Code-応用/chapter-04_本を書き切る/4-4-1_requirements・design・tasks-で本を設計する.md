# 4-4-1 requirements・design・tasks で本を設計する

Part3 で、本のプロジェクト `my-book` に前提（CLAUDE.md）・目次（OUTLINE.md）・文体（rules）を整え、第1章を書き、執筆スキルを作りました。Part4 の前半では、こうした機能を束ねて「ハーネス」（AI を確実に働かせる仕組みの集まり）にし、仕組みとして再利用する考え方を学びました。この Chapter では、そのハーネスを本格化し、仕様駆動で本を1冊書き切ります。

**この Chapter の進め方**: Part3 で育てた `my-book` を引き継ぎ、仕様（requirements・design・tasks）に正式化し、サブエージェントと設定を足して、残りの章を書き切ります。前のセクションの成果物を使うので、順番に進めてください。

!!! note "前提知識"
    このセクションは 3-5-5「skill-creator で執筆をスキルにする」と 4-2-3「要件・設計・タスクの3段で固める」の内容を前提としています。

!!! note "このハンズオンで使う機能"
    仕様駆動の3段（要件＝requirements・設計＝design・タスク＝tasks。Part4 で学習）を使います。Part3 で「全部 CLAUDE.md／OUTLINE.md」に書いた前提と目次を、題材ごとの仕様ファイルに変身させます。

## このセクションで学ぶこと

- `CLAUDE.md`（前提）と `OUTLINE.md`（目次）を `docs/<題材>/requirements.md`・`design.md` に書き起こす
- 新しく `docs/<題材>/tasks.md`（章ごとの執筆・検証タスク）を作る
- 本文 `chapters/` を `output/<題材>/` に移す
- 構造が変わったので、`CLAUDE.md` を入口に書き換え、`OUTLINE.md` を削除し、rules・執筆スキルを新しい構造に合わせて直す
- 人が採否を判断して、仕様を「正」として確定する

「全部 CLAUDE.md」から「仕様（docs/）を正に、題材ごとに量産」へ移行します。

---

## 導入: 「全部 CLAUDE.md」の限界

Part3 では、前提も目次も CLAUDE.md と OUTLINE.md にまとめ、スキルで呼べば章が書ける状態を作りました。1〜2章ならこれで十分です。けれど、1冊を最後まで書き切ろうとすると、いくつか足りません。前提と目次が混ざっていて全体を見直しにくい、章ごとの作業が一覧になっていない、2冊目を書こうとすると同じ仕組みを作り直すことになる、といった点です。

そこで、Part4 で学んだ仕様駆動を使い、本を「仕様」として固めます。仕様を正（よりどころ）にすれば、本文は仕様から作られる出力物になり、全体を見渡しながら量産できます。Part3 で作った素朴な構成を、次のように変身させます。

```text
Part3 までの my-book/            この Chapter で仕様駆動に変身
─────────────────────         ─────────────────────────────────
CLAUDE.md（前提）        →      docs/<題材>/requirements.md（要件）
OUTLINE.md（目次）       →      docs/<題材>/design.md（設計）
                               docs/<題材>/tasks.md（タスク・新規）
chapters/（本文）        →      output/<題材>/（本文）
.claude/（rules・skills） →      .claude/（rules・skills…題材をまたいで共有）
```

変身といっても、すべてのファイルが置き換わるわけではありません。OUTLINE.md は中身を design.md に移すので削除し、CLAUDE.md は題材ごとの要件を requirements.md に移したうえで、「仕様は docs/（題材名）/ にある」と指し示す入口として残します（CLAUDE.md は起動時に自動で読まれるので、どの題材の仕様を見ればよいかが分かる状態を保つため）。

`docs/<題材>/` と `output/<題材>/` は題材ごとに分かれるので、`.claude/` のハーネスを共有したまま、2冊目以降も同じ仕組みで書けます。なお、ここでは仕様の「形」を手で固めます。同じ形を道具に自動生成させるやり方（cc-sdd）は、アプリ開発の Part6 で扱います。

!!! note "補足: もとはソフトウェア開発で使う3点セット"
    `requirements.md`（要件）・`design.md`（設計）・`tasks.md`（タスク）という3点の構成は、もともとソフトウェア開発の仕様駆動開発（SDD。4-2 で学習）で使われるものです。アプリを作る前に「要件（何を作るか）→ 設計（どう作るか）→ タスク（作業を分解）」と仕様を固める形を、ここでは本づくりに応用しています。題材は違っても、「作り始める前に仕様を固め、それを正とする」という考え方は、開発でも執筆でも同じように効きます。Part6 では、この3点を実際のアプリ開発で（道具に自動生成させて）扱います。

## 実践: 本を仕様（requirements・design・tasks）に正式化する

### Step 1: 題材ごとのフォルダを決める

本（題材）ごとに、仕様を置く `docs/<題材>/` と、本文を置く `output/<題材>/` を用意します。`<題材>` は自分の本が分かる短い名前にします（例: `intro-marketing`）。複数の本を書くときは、この単位で分けます。

```text
（Claude への依頼）
my-book の中に docs/（題材名）/ と output/（題材名）/ のフォルダを用意してください。
```

### Step 2: requirements.md と design.md を生成する

前提（CLAUDE.md）と目次（OUTLINE.md）を、まとめて仕様ファイルに書き起こさせます。完成条件は、定型の記法に凝らず「○○のとき△△ができている」という言葉で書かせます（Part4 で学んだとおり）。元ファイルの整理や道具の修正は、構造がそろう Step 5 でまとめて行うので、ここでは生成に集中します。

```text
my-book の前提と目次を、題材ごとの仕様ファイルに書き起こしてください（元の CLAUDE.md・OUTLINE.md はまだ残しておいてください）。
- CLAUDE.md の前提（誰に・何を・狙い・完成条件）→ docs/（題材名）/requirements.md（完成条件は「○○のとき△△ができている」の言葉で）
- OUTLINE.md の目次 → docs/（題材名）/design.md（各章の狙い・前後の順序・制約まで）
判断に迷う点があれば、勝手に決めず AskUserQuestion で質問してください。
```

返ってきた requirements.md と design.md を読んで、狙いと合うように直し、自分で「これが正」と確定します。

### Step 3: tasks.md を作る

設計をもとに、章ごとの「執筆・検証タスク」を `docs/<題材>/tasks.md` に新しく作ります。完成条件は requirements.md にあるので、tasks.md には書き写しません。各章を「書く → requirements.md のその章の完成条件で検証する」という作業の段取りとして並べます。これが、残りの章を1つずつ書き切るときの作業リストになります。

```text
design.md と requirements.md をもとに、章ごとの執筆・検証タスクを docs/（題材名）/tasks.md に作ってください。
各章は「書く → requirements.md のその章の完成条件で検証する」の形で並べ、完成条件そのものは requirements.md を参照してください（tasks.md には書き写さない）。
```

### Step 4: 本文を output/ に移す

Part3 で書いた第1章（`chapters/`）を、`output/<題材>/` に移します。以降、本文はここにたまっていきます。

```text
chapters/ にある第1章を output/（題材名）/ に移してください。
```

### Step 5: 構造が変わったので道具を整える

ここまでで、仕様（docs/）と本文（output/）の新しい構造ができました。最後に、元のファイルと道具が、この新しい構造を正しく指すように整えます。CLAUDE.md・rules・執筆スキルが古い場所（OUTLINE.md や chapters/）を参照したままだと、次の章を書くときにかみ合いません。

```text
my-book を新しい構造に合わせて整えてください。
- CLAUDE.md は、題材ごとの要件を requirements.md に譲り、「この本の仕様は docs/（題材名）/ にある（requirements・design・tasks を正とする）」と全体の入口に書き換える
- 目次は design.md に移したので、OUTLINE.md は削除する
- .claude/rules/ の文体ルールと .claude/skills/ の執筆スキルが、古い参照（OUTLINE.md や chapters/）を含んでいたら、新しい構造（docs/（題材名）/。本文は output/（題材名）/ に書く）に合わせて直す
```

CLAUDE.md が入口に書き換わり、OUTLINE.md が消え、執筆スキルが新しい構造（design.md・tasks.md を見て `output/<題材>/` に書く）を指していることを確認します。これで、次の章から執筆スキルを呼ぶだけで、新しい構造の上で書けます。

## できあがったディレクトリ構成

ここまでで、`my-book` は次の形になりました。前提と目次が `docs/<題材>/` の仕様（requirements・design・tasks）に変わり、本文が `output/<題材>/` に移っています。

```text
my-book/
├── CLAUDE.md                  # 仕様の在りかを指す入口（書き換え済み）
├── docs/
│   └── <題材>/
│       ├── requirements.md    # 要件（誰に・何を・各章の完成条件）
│       ├── design.md          # 設計（各章の狙い・順序・制約）
│       └── tasks.md           # タスク（章ごとの作業の段取り）
├── output/
│   └── <題材>/
│       └── 01-….md            # 第1章（chapters/ から移動）
└── .claude/
    ├── rules/                 # 文体ルール（題材をまたいで共有）
    └── skills/                # 執筆スキル（題材をまたいで共有）
```

`OUTLINE.md` は `design.md` に移したので、もうありません。`docs/` と `output/` は題材ごとに分かれるので、2冊目は `docs/<題材B>/` と `output/<題材B>/` を足すだけで、同じ `.claude/` を使って書けます。

## まとめ

- 「全部 CLAUDE.md」では1冊の量産に足りない。仕様駆動で要件・設計・タスクに分け、仕様を正にする
- `CLAUDE.md` の要件→requirements、`OUTLINE.md`→design、新規 tasks、`chapters/`→output と変身させ、題材ごとに分ける。CLAUDE.md は仕様の在りかを指す入口として残し、OUTLINE.md は削除する
- 仕様の形は手で固める。同じ形を道具に自動生成させるのは Part6（cc-sdd）。`.claude/` は題材をまたいで共有でき、2冊目も同じ仕組みで書ける
