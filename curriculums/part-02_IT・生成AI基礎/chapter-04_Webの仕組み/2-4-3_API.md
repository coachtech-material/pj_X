# 2-4-3 API

!!! note "前提知識"
    このセクションは 2-4-2「Webアプリの仕組み」の内容を前提としています。

## このセクションで学ぶこと

- API が「サービス同士が決まった窓口（要求と応答）でやり取りする仕組み」であること
- やり取りに JSON のような決まった形のデータが使われること
- API が、外部サービス連携（MCP）や自作アプリの土台になること

API とは何かを HTTP の延長として押さえ、やり取りされるデータの形と、API が土台になるものを見ていきます。

!!! note "補足"
    このセクションの本文に出てくるデータの例は、読んで形をつかむための例です。鍵や認証の実装は AI に任せるため扱いません。API を使うものを実際に AI に作らせるのは、Part6 のアプリ開発で扱います。

---

## 導入: サービス同士は、どうつながっているのか

予約アプリが地図サービスの場所を表示する。家計簿アプリが銀行の残高を読み込む。別々の会社が作ったサービスが、互いのデータをやり取りしています。人どうしなら画面を見て操作しますが、サービス同士は画面を介しません。プログラムが直接データをやり取りするための「窓口」を使います。その窓口が、これから学ぶ API です。

---

## API: 決まった窓口でのやり取り

**API** は、あるサービスが外部に向けて用意した、決まった窓口です。「この形で要求を送れば、この形で応答を返します」という約束を決めておき、その窓口を通じてプログラム同士がデータをやり取りします。

仕組みは、2-4-1 で見た HTTP の延長です。人がブラウザで見る画面の代わりに、プログラム向けの窓口にリクエストを送ると、レスポンスが返ってくる。違いは、返ってくるのが「人が見る画面」ではなく「プログラムが扱いやすいデータ」だという点です。

レストランのたとえで言えば、画面が客席なら、API は出前の注文窓口です。決まった様式で注文すれば、決まった形で品物が届きます。

## やり取りには決まった形のデータ（JSON）

API のやり取りでは、**JSON** （2-1-3 で触れた形式）のような、決まった形のデータがよく使われます。たとえば天気を知らせる API に「東京」を尋ねると、こんな応答が返ってきます。

```json
{
  "city": "Tokyo",
  "temperature": 28,
  "weather": "晴れ"
}
```

名前（`city`）と値（`Tokyo`）の組で並んでいるので、受け取ったプログラムは「気温は 28 だ」と正確に取り出せます。人が読む文章だと解釈の余地が残りますが、決まった形のデータなら、プログラムが迷わず扱えます。

## API が土台になるもの

この「決まった窓口でやり取りする」仕組みは、本研修の後半で何度も土台になります。

- **外部サービス連携（MCP）**: AI を社内外のサービス（カレンダー・スプレッドシート等）につなぐ仕組み（3-4-1 で扱う MCP）は、この API の考え方の上に成り立っています。
- **自作アプリ**: Part6 で作るアプリでも、画面とサーバの間、外部サービスとの間で、API を通じてデータをやり取りします。

なお、API を使うとき、相手が許可した利用者かを確かめるために鍵（API キー）などが要ることがあります。その仕組みは 2-4-4（認証と認可）で、鍵の扱いの注意は 2-5-3（セキュリティ）で扱います。鍵を使う実装そのものは AI に任せるので、ここでは「そういう確認が要ることがある」とだけ押さえれば十分です。

---

## まとめ

- API は、サービスが外部に用意した「決まった窓口」。HTTP の延長で、プログラム同士がデータをやり取りする
- やり取りには JSON のような決まった形のデータが使われ、受け取った側が値を正確に取り出せる
- API は、AI を外部サービスにつなぐ MCP（3-4-1）や、自作アプリの土台になる
