## 実践: 開発のハーネスを整える

### Step 1: auto モードに上げる

本づくりでは、編集を自動承認する acceptEdits を使いました。アプリ開発はより長く自律的に動かすので、もう一段上の auto モードを使います。

auto モードでは、別の分類器（安全チェック専用のモデル）がアクションを実行前に毎回レビューし、危険なものだけを止めます。ふだんのファイル編集やコマンド実行は確認なしで進み、止まるのは次のような高リスクな操作です。

- 本番環境への公開（デプロイ）や、本番データベースへの反映（マイグレーション）
- `main` への直接 push や、変更を強制的に上書きする push
- コミットしていない変更を破棄する操作（`git reset --hard` など）
- 秘密のデータを外部に送る、知らないインフラを操作する、といった動き

つまり、auto にしても、公開や本番反映のような取り返しのつかない操作は分類器が一度止めて確認を求めます。だから安心して長時間任せられます。

auto モードへの切り替えは、Part3 で学んだのと同じ `Shift + Tab` で行います。`ai-minutes` フォルダで Claude Code を起動し、`Shift + Tab` を何回か押して権限モードを切り替えていくと auto が選べます。初回は「auto にしてよいか」の確認が出るので、受け入れます。ステータス行が auto の表示に変わったら、切り替え完了です。

!!! warning "注意"
    auto モードはリサーチプレビュー（試験提供）で、対応するバージョン（2026年6月時点で v2.1.83 以降）と対応モデル（Claude Opus 4.6 以降または Sonnet 4.6）が必要です。条件を満たさないと `Shift + Tab` の循環に auto が出てきません。安全チェックは付きますが安全を保証するものではないので、機密に関わる操作の確認をこれに置き換えてはいけません。毎回 auto で始めたい場合は、起動時に `claude --permission-mode auto` と指定するか、自分用の設定（`~/.claude/settings.json`）に `defaultMode` を書きます（プロジェクトの設定ファイルに書いた auto は、安全のため無視されます）。

ずれに気づいたら、本づくりと同じく `Esc` で途中で止め、`/rewind` で前の状態に戻せます。auto モードは、分類器が続けて操作を止めると自動で一時停止し、確認を求める状態に戻ります。

### Step 2: 最新ドキュメントを引く MCP を接続する

実装中は「この書き方は今のバージョンで正しいか」を確かめたい場面が出ます。検索して自分で調べるのではなく、Claude Code が最新のドキュメントをその場で引けるようにします。ここでは、ライブラリの最新ドキュメントを返す MCP サーバー context7 を接続します。

`ai-minutes` フォルダで（Claude Code の外のターミナルで）次を実行します。

```bash
claude mcp add --transport http context7 https://mcp.context7.com/mcp
```

接続できたか確認します。

```bash
claude mcp list
```

一覧に context7 が出れば接続できています。これで、実装中に「Next.js の最新の書き方を context7 で確認して」のように頼めば、Claude Code が最新ドキュメントを参照して判断できます。技術的な迷いを、検索ではなく Claude Code との対話で解けるようになります。

!!! note "補足"
    context7 は API キーなしでも基本の範囲で使えます。利用が多く上限に届く場合は、context7 のサイトで無料のキーを取得し、`--header "CONTEXT7_API_KEY: 取得したキー"` を付けて接続すると上限が上がります（2026年6月時点）。キーは秘密の値なので、公開リポジトリに含めないよう扱います。

### Step 3: 秘密の値を読み取り禁止にする

アプリでは、API キーなどの秘密の値を `.env` や `.dev.vars`（雛形にあったローカル用の秘密ファイル）に置きます。これらを Claude Code が読まないように、読み取り自体を禁止しておきます。設定ファイルは自分で手書きせず、Claude Code に作ってもらいます。

Claude Code に次のように頼みます。

```text
.claude/settings.json の permissions に deny を足して、.env と .dev.vars を読み取り禁止にしてください。ファイルが無ければ新規に作成してください。
```

`.claude/settings.json` が次のような形になっているか確認します（一例。あなたのものと細部が違ってかまいません）。

```jsonc
// ai-minutes/.claude/settings.json（Claude が作る。形の一例）
{
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Read(./.dev.vars)"
    ]
  }
}
```

これで、秘密の値がうっかり会話に取り込まれて外部に渡る、といった事故を防げます。これらのファイルを Git に上げない設定は、雛形の `.gitignore` に最初から入っています。「読み取らない（deny）」と「上げない（.gitignore）」の両面で、秘密を守ります。

### Step 4: モデルと努力レベルのコスト方針を決める

すべての作業に最上位のモデルや最大の努力レベルを使うのは無駄です。本づくりで学んだコストの考え方を、開発にも当てます。

- 仕様の設計や、難しい不具合の調査など、考える比重が高いところは上位モデル・努力レベルを上げる
- ふだんの実装や定型の修正は、軽め・速めのモデルで回す

切り替えは `/model` や `/effort` で行えます。目安として、cc-sdd 自身も「設計やレビューは上位モデル、実装は標準のモデル」を推奨しています（2026年6月時点）。重さに応じて使い分け、無駄なコストを避けます。

### Step 5: 長いビルドに備えてコンテキスト管理を確認する

実装は長くなり、会話のコンテキストが膨らみます。膨らんだまま続けると精度が落ちるので、整える手段を確認しておきます（いずれも Part3 で学んだものです）。

- `/context`: いまどれくらいコンテキストを使っているか確認する
- `/compact`: 膨らんだ会話を要約して圧縮する（観点を添えると要点を保ちやすい）
- `/rename`: 区切りのよいところでセッションに名前を付けて残す
- `exit` と `claude --resume`: いったん終えて、続きを別のときに同じ文脈から再開する
- `/clear`: 無関係な作業に移るとき、いまの会話を捨ててリセットする（あとで戻りたいときは使わない）

実装の途中で「データ基盤ができた」「画面ができた」といった区切りごとに整えると、長いビルドでも精度を保てます。

## まとめ

- auto モードは、分類器がデプロイ・本番反映・main 直 push・破壊的な操作だけを止め、ふだんの作業は確認なしで進める。`Shift + Tab` で切り替え、ずれは Esc・/rewind で戻す
- context7 などの MCP を接続すると、技術判断を検索ではなく Claude Code との対話で確かめられる
- 秘密の値（.env・.dev.vars）は `deny` で読み取り禁止にし、`.gitignore` と合わせて二重に守る
- モデル・努力レベルは重さで選び分け、長いビルドではコンテキストを積極的に整える

この章では、何を作るかの全体像を持ち、開発環境と Cloudflare をそろえ、cc-sdd で仕様駆動の土台（steering）を作り、auto モード・MCP・機密の線引き・コスト方針という開発のハーネスを整えました。長時間の自律実装に踏み出す足場がそろいました。
