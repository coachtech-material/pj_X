# 6-2-1 cc-sddで要件・設計・タスクを固める

この章では、固めた仕様を地図にして、AI 議事録アプリを実際に動く形まで組み上げます。まず cc-sdd で要件・設計・タスクを固め（このセクション）、その仕様に沿ってデータ基盤・AI 要約・画面を順に実装します。

| セクション | テーマ | 種類 |
|---|---|---|
| 6-2-1 | cc-sdd で要件・設計・タスクを固める | ハンズオン |
| 6-2-2 | データ基盤を作る | ハンズオン |
| 6-2-3 | AI 要約機能を作る | ハンズオン |
| 6-2-4 | 画面を作ってつなぐ | ハンズオン |

**この章の進め方**: 仕様を固める（このセクション）→ データの保存と出し入れ → AI で要約 → 画面でつなぐ、の順に、各段を完成条件で確かめながら積み上げます。

!!! note "前提知識"
    このセクションは、開発のハーネス（6-1-4）、仕様駆動を要件・設計・タスクの3段で固める考え方（4-2-2）、本づくりでその3段を手で固めた経験（4-4-1）、完成条件で確かめる検証ゲート（3-1-6）を前提とします。

!!! note "このハンズオンで使う機能"
    cc-sdd の仕様づくりのスキル（`/kiro-spec-init`・`/kiro-spec-requirements`・`/kiro-spec-design`・`/kiro-spec-tasks`）を使います。本づくりで手で固めた「要件→設計→タスク」を、ここでは道具に決まった形で生成させ、各段を自分で確認して正にします。

## このセクションで学ぶこと

- cc-sdd で要件（完成条件を含む）→設計→タスクを生成し、各段を確認して採用・修正・差し戻しを判断する
- 設計では、固定した技術スタックの枠内で、データの持ち方や API の切り方を Claude Code と対話して決める
- 生成されたタスクが実装の地図になり、各タスクに完成条件と検証がひも付くことを確認する

本づくりで手で固めた仕様の形を、ここでは道具が自動で生成します。

---

## 導入: 作り始める前に仕様を「正」にする

アプリ開発で「議事録アプリを作って」といきなり丸投げすると、画面の見た目・データの持ち方・AI の使い方など、決めていない部分を Claude Code が解釈で埋め、狙いとずれていきます。本づくりで学んだとおり、大きい仕事ほど、作り始める前に仕様を固めるほど後がぶれません。

cc-sdd を使うと、この「要件→設計→タスク」を決まった形で生成できます。大事なのは、生成された各段を自分で読んで判断することです。cc-sdd は要件・設計・タスクの3段に分け、各段で人の確認を挟んでから次へ進む作りになっています。あなたは「何を作りたいか（What）」の番人として、各段を採用するか・直すか・やり直すかを決めます。

## 実践: 要件・設計・タスクを固める

### Step 1: 仕様づくりを始める

作る機能の説明を渡して、仕様づくりを始めます。`/kiro-spec-init` に続けて、作るものを説明します。

```text
/kiro-spec-init AI 議事録アプリ。会議のメモを貼り付けると、AI が要約・決定事項・ToDo に整形して保存し、あとから一覧・検索できる社内向けツール。技術は Next.js（画面と Route Handler）・Cloudflare D1（保存）・Cloudflare Workers AI（要約）。認証は作らず、1人で使うデモとして公開する。
```

Claude Code は、この説明から機能の名前を決め（たとえば `meeting-minutes` のような名前。あなたのものは違ってかまいません）、`.kiro/specs/（機能名）/` フォルダに仕様づくりの土台を作ります。以降のコマンドでは、この機能名を使います（ここでは `（機能名）` と書きます）。

### Step 2: 要件を生成して完成条件を確認する

要件を生成します。

```text
/kiro-spec-requirements （機能名）
```

`.kiro/specs/（機能名）/requirements.md` が作られ、「誰が・何を・なぜ」と、完成条件が並びます。完成条件は「○○のとき、△△ができる」という形で書かれます。たとえば次のような項目です（これは一例で、生成される文面はあなたのものと違ってかまいません）。

- メモを貼り付けて整形を実行すると、要約・決定事項・ToDo が表示される
- 整形した記録を保存すると、一覧に表示される
- キーワードで検索すると、該当する記録だけが表示される

ここが最初の判断どころです。requirements.md を読み、作りたいものと合っているかを確認します。足りない条件があれば「検索は本文だけでなく日付でもできるようにして」のように伝えて直してもらい、自分が「これでよい」と思える状態にしてから次へ進みます。

!!! note "補足"
    この完成条件は、本づくりで決めた「○○のとき△△ができていること」と同じ考え方です。cc-sdd はこれを決まった形式でそろえてくれます。形式の名前を覚える必要はありません。読んで「作りたいものと合っているか」を判断できれば十分です。

### Step 3: 設計を生成し、How を対話で決める

要件が固まったら、設計を生成します。

```text
/kiro-spec-design （機能名）
```

`.kiro/specs/（機能名）/design.md` に、どう作るか（技術スタック、データの持ち方、API の切り方、画面の構成など）が書かれます。技術スタックは最初に固定したもの（Next.js・Cloudflare D1・Workers AI）の枠内で、具体は Claude Code が設計します。

ここで、How（作り方）の具体を Claude Code と対話して決めます。たとえば「メモはどんな列で保存するか（本文・要約・決定事項・ToDo・作成日時）」「API はどんな窓口にするか（保存する窓口・一覧を返す窓口）」です。決めたら、なぜそうしたかを一言 design に残してもらうと、あとで読み返せます。技術判断に迷ったら、土台づくりで接続した context7 で最新の書き方を確認しながら決められます。

### Step 4: タスクに分解する

設計が固まったら、タスクに分解します。

```text
/kiro-spec-tasks （機能名）
```

`.kiro/specs/（機能名）/tasks.md` に、検証できる小さなタスクが番号付きで並びます。各タスクには、何をするか・何ができたら完了か（完成条件）・どう確かめるか（テストや動作確認）がひも付きます。これが、このあと実装を進める順番を示すものになります。

tasks.md を読み、データ基盤・AI 要約・画面という大きな流れに沿って、タスクが順序立っているかを確認します。

### Step 5: 固めた仕様を実装の出発点として確認する

ここまでで、`.kiro/specs/（機能名）/` に requirements.md・design.md・tasks.md の3つがそろいました。本づくりでは、これと同じ「要件・設計・タスク」を手で書き起こしました。Part6 では、同じ形を cc-sdd が自動で生成しています。手で書くか道具に書かせるかが違うだけで、「作る前に仕様を正として固める」進め方は同じです。

この3つを正（よりどころ）として、次のセクションから実装に入ります。実装中に「やっぱりこう変えたい」と思ったら、コードを直す前に仕様（design・tasks）を直してから進めると、仕様と実物がずれません。

## まとめ

- cc-sdd の `/kiro-spec-init`→`/kiro-spec-requirements`→`/kiro-spec-design`→`/kiro-spec-tasks` で、要件・設計・タスクを決まった形で生成できる
- 各段は人が確認してから次へ進む。採用・修正・差し戻しは自分で判断する
- 設計では、固定スタックの枠内で、データの持ち方や API の切り方を Claude Code と対話して決める
- 生成された tasks が実装の道筋になる。本づくりで手で固めた仕様の形を、ここでは cc-sdd が自動生成している

---

次のセクションでは、固めた tasks の該当タスクから、データベース（Cloudflare D1）の用意と、メモを登録・取得する API（Next.js の Route Handler）を Claude Code に実装させます。API の期待する動きをテストで先に決めて通るまで直させる検証ゲートを体験し、メモを保存・取得できることをローカルで確認します。
