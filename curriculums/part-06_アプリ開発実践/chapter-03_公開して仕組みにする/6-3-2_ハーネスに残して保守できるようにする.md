# 6-3-2 ハーネスに残して保守できるようにする

!!! note "前提知識"
    このセクションは、デプロイして公開したアプリ（6-3-1）、資産化して属人化を解消する考え方（4-1-3）、Skill（Part3）、サブエージェント（Part3）、hooks（Part3）、テストと TDD（2-2-3）を前提とします。

!!! note "このハンズオンで使う機能"
    Skill（手順を残す）、CLAUDE.md・steering・`settings.json`（前提を残す）、コードを別文脈でレビューする仕組み（公式の `/code-review` または検証サブエージェント）、コミット前にテストを通す Stop hook を使います。これまで個別に学んだ機能を、保守できる仕組みとして束ねます。

## このセクションで学ぶこと

- 開発で繰り返した手順（環境準備・実装・検証・デプロイ）を Skill に残す
- アプリの前提を CLAUDE.md・steering・設定に残し、コードを多観点でレビューする仕組みを入れる
- コミット前にテストを通す歯止め（Stop hook）を入れ、属人化が解けることを確かめる

一度作ったアプリを、二度目以降も安全に直し続けられる状態にします。

---

## 導入: 二度目を速く、安全にする

アプリは公開して終わりではありません。要約の精度を上げたい、項目を増やしたい、不具合を直したい、と手を入れ続けます。そのとき、毎回ゼロから段取りを思い出したり、直した拍子に別の場所を壊したりすると、保守がつらくなります。

ここで思い出したいのは、cc-sdd を導入した時点で、すでに多くがハーネスとして整っていることです。仕様を生成・実装するスキル（`/kiro-spec-*` や `/kiro-impl`）と、プロジェクトの前提（steering）は、もう手元にあります。とくに `/kiro-impl` は、実装からレビュー・検証までをこなします。

このセクションでやるのは、その上に、cc-sdd がカバーしない部分を足すことです。具体的には、このアプリ固有の公開（デプロイ）の段取りを Skill にまとめ、開発で決めたことを steering に反映して最新に保ち、公開する変更を独立した目でレビューする仕組みと、コミット前にテストを通す歯止めを入れます。こうしておくと、次の変更からは「呼ぶ・仕組みが守る」だけで、速く安全に進められます。

## 実践: 開発をハーネスに残す

### Step 1: 公開の段取りを skill-creator でスキルにする

実装そのものの段取り（仕様の確認→実装→レビュー→検証）は、cc-sdd の `/kiro-impl` がすでに担っています。同じものを重ねて作る必要はありません。一方で、公開の一連（本番データベースへの反映→デプロイ→公開 URL の検証）は、cc-sdd の標準にはない、このアプリ固有の手順です。これを次から呼び出せる Skill にまとめます。

本づくりで導入した skill-creator（公式プラグイン）を、ここでも使います。`/skill-creator` に続けて、どんなスキルにしたいかを伝えます（もし `/skill-creator` が見つからないときは、本づくりのときと同じ手順でプラグインを入れ直します）。

```text
/skill-creator このアプリを公開する手順（本番 D1 へのマイグレーション反映 → npm run deploy → 公開 URL を Playwright で検証）を読み取って、呼び出すだけで公開できるスキルにしてください。スキルは ai-minutes の .claude/skills/ に作ってください。
```

skill-creator は手順を読み取って `SKILL.md`（スキルの名前・説明・手順）を作ります。名前・説明・手順を確認して整えれば、次に変更を公開するときは、このスキルを呼ぶだけで同じ手順で安全にデプロイできます。

### Step 2: 決めたことを steering に反映して最新に保つ

アプリの前提（技術構成・データの持ち方・運用のルール）は、土台づくりで作った steering にすでに集まっています。新しく作るのではなく、開発の過程で決めたこと（たとえば「要約に使うモデル」「テーブルの列の意味」「公開の手順」）が steering に反映されているかを確認し、抜けていれば追記して最新に保ちます。cc-sdd には steering を更新するスキル（`/kiro-steering`）があるので、これで同期できます。あわせて、土台づくりで作った `settings.json`（権限・`deny`）も、公開後の運用に合っているかを見直します。

steering が最新なら、別の日に新しいセッションで開いても、前提はファイルから自動で読み込まれ、同じ理解で作業を再開できます。

### Step 3: コードを多観点でレビューする仕組みを入れる

変更を加えたとき、その変更が完成条件を満たすか・余計な場所を変えていないかを、別の目で確認します。cc-sdd の `/kiro-impl` も実装時に検証しますが、ここでは、公開する変更（diff）を独立した文脈でもう一度見ます。自分が書いた（書かせた）コードを同じ文脈で見直すより、新しい文脈で見るほうが、思い込みに気づけます（Part4 の敵対的レビューの考え方）。

手軽なのは、公式の `/code-review` を使う方法です。

```text
/code-review
```

これは、いまの変更（diff）を別のサブエージェントがレビューして、問題点を報告します。より自分のアプリに合わせたい場合は、本づくりで作ったような検証サブエージェントを `.claude/agents/` に用意し、「完成条件を満たすか・スコープ外を変えていないか」を指摘させることもできます。どちらの場合も、指摘を採用するかは自分で判断します。

!!! info "ポイント"
    レビューは、指摘を求めればたいてい何か返ってきます。すべてに対応すると、かえって作り込みすぎになります（過剰な防御やめったに起きないケースの作り込み）。「完成条件や正しさに関わる指摘」だけを直し、残りは任意として扱う、と決めておくと、保守が軽くなります。

### Step 4: コミット前にテストを通す歯止めを入れる

データ基盤づくりでは、テストを書いて検証しました。これを「毎回必ず通っているか」の歯止めにします。コミットの前にテストを自動で実行し、失敗したらコミットを止める仕組みを、hooks で入れます。CLAUDE.md の指示と違い、hooks は決まったタイミングで確実に実行されます（Part3）。Claude Code に書いてもらいます。

```text
コミットする前にテストを実行して、失敗したらコミットを止める hook を settings.json に書いてください。
```

これで、テストが通らない変更がうっかり記録されることを防げます。hooks は効果の高いものを1つから始めます（あれもこれもと入れると、毎回の動作が重くなります）。

!!! warning "注意"
    hook を入れたら、わざとテストを失敗させて、コミットが止まることを一度確かめます。発火しない・止まらないときは、その様子を Claude Code に伝えて直してもらいます。動きを確認しないまま入れると、効いているつもりで効いていない、という状態になりがちです。

## まとめ

- 実装の段取りは cc-sdd の `/kiro-impl` が担う。公開（デプロイ）の段取りなど、cc-sdd にない固有の手順を Skill に残す
- アプリの前提は steering に集約済み。開発で決めたことを反映して最新に保てば、新しいセッションでも同じ理解で再開できる
- 変更は `/code-review` や検証サブエージェントで別の文脈からレビューし、完成条件と正しさに関わる指摘を採用する
- コミット前にテストを通す Stop hook で、品質の歯止めを自動化する。やり方がプロジェクトに資産化され、属人化が解ける

---

次のセクションでは、作ったアプリで削減できる時間や件数を見積もって、内製ツールの価値（成果指標）に接続します。あわせて、課題を定め・AI に実行させ・確かめて仕上げ・残し共有し・仕組みにする一連が、書籍に続いて実アプリ開発でも一周したことを振り返り、プロンプト→コンテキスト→ハーネスの全体像を整理して、研修全体を締めくくります。
