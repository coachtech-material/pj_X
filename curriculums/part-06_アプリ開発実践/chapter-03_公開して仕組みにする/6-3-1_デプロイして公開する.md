# 6-3-1 デプロイして公開する

この章では、ローカルで動くようになったアプリを世に出し、その手順を仕組みに残し、最後に研修全体を締めくくります。

| セクション | テーマ | 種類 |
|---|---|---|
| 6-3-1 | デプロイして公開する | ハンズオン |
| 6-3-2 | ハーネスに残して保守できるようにする | ハンズオン |
| 6-3-3 | 業務成果に接続して締めくくる | 混合 |

**この章の進め方**: アプリを公開して動作を検証する（このセクション）→ 開発の手順をハーネスに残して保守できるようにする → 作ったアプリを業務成果に接続し、研修全体を振り返る。

!!! note "前提知識"
    このセクションは、ローカルで動くアプリ（6-2-4）、成果物を GitHub に上げる操作（5-2-3）、機密を AI に渡さない判断（2-5-3）を前提とします。

!!! note "このハンズオンで使う機能"
    Git（記録）、環境変数・シークレット（秘密の値の扱い）、Cloudflare への公開（`wrangler` / `npm run deploy`）、本番データベース（remote D1）への反映、そして公開後のアプリを Claude Code から操作して検証する Playwright の MCP を使います。

## このセクションで学ぶこと

- アプリのコードを Git で記録し、秘密の値を分けて扱う
- 本番データベース（remote D1）に反映し、Cloudflare に公開（デプロイ）して公開 URL を得る
- 公開後のアプリを Claude Code（Playwright の MCP）で操作し、完成条件を満たすか検証する

ローカルで動くアプリを、誰でも使える形でインターネットに出します。

---

## 導入: ローカルで動くアプリを公開する

ここまでで、アプリは自分のパソコンの中（ローカル）で動いています。最後の仕上げは、これを Cloudflare に公開（デプロイ）して、公開 URL で誰でも開ける状態にすることです。

公開では、ローカルとは別に本番の置き場を用意します。具体的には、本番のデータベース（remote D1）にテーブルを反映し、アプリ本体を Cloudflare に送り出します。ここは取り返しのつかない操作（本番への反映・公開）を含むので、土台づくりで触れたとおり、auto モードでも分類器が一度手を止めて確認を求めます。表示を読んで、自分で承認しながら進めます。これが暴走を防ぐ安全策になっています。

- [ ] `ai-minutes` フォルダで Claude Code を起動している（auto モード）

## 実践: Cloudflare に公開する

### Step 1: コードを Git で記録し、秘密の扱いを確認する

公開の前に、ここまでの変更を Git で記録します。雛形を作ったときに最初のコミットができていれば、それ以降の変更をコミットします（最初のコミットが無ければ、それも含めて作ってもらいます）。Claude Code に頼みます。

```text
ここまでの変更を、わかりやすいメッセージでコミットして。
```

秘密の値（API キーやパスワード）は、コードに直接書かず、Git にも上げません。このアプリは Cloudflare のバインディング（`AI`・`DB`）だけで動くので、コードに書く外部の鍵はありません。もし外部サービスを使う場合は、本番の鍵は次の Step で使う `wrangler secret put` で Cloudflare に登録し、ローカル用は `.dev.vars` に置きます。どちらも `.gitignore` で Git から除外されています。必要に応じて、Part5 で学んだように GitHub へ push しても構いません。

!!! note "補足"
    秘密の値を「コミットしない（`.gitignore`）」と「AI に読ませない（`deny`）」の両方で守る、という考え方は、アプリでも本（書籍）でも同じです。公開リポジトリに鍵が混ざる事故を、仕組みで防ぎます。

### Step 2: 本番データベースにテーブルを反映する

ローカルでは、自分のパソコンの中のデータベースを使っていました（`--local`）。公開するアプリは、本番のデータベース（remote D1）を使います。そこで、本番のデータベースにも同じテーブルを作ります。Claude Code に頼みます。

```text
本番の D1 データベースに、これまでのマイグレーションを反映して。
```

Claude Code は `npx wrangler d1 migrations apply ai-minutes-db --remote` のようなコマンドを実行します。`--remote` は本番のデータベースへの反映を意味します。これは取り返しのつかない操作なので、auto モードでも確認を求められます。内容（本番の `ai-minutes-db` に反映すること）を確認して承認します。

### Step 3: デプロイして公開 URL を得る

アプリ本体を Cloudflare に公開します。`ai-minutes` フォルダで、デプロイのコマンドを実行します。

```bash
npm run deploy
```

このコマンドは、アプリを公開用に組み立て（ビルド）、Cloudflare に送り出します（デプロイ）。本番への公開も取り返しのつかない操作なので、auto モードでは確認を求められます。承認して進めます。

完了すると、`ai-minutes.（あなたのサブドメイン）.workers.dev` のような公開 URL が表示されます。ブラウザでその URL を開くと、自分のアプリがインターネット上で動いています。

!!! note "補足"
    先に AI バインディングに付けた remote bindings（`experimental_remote`）は、ローカル開発で実際の Cloudflare につなぐための設定でした。公開したアプリは初めから Cloudflare 上で動くので、本番では AI も D1 もそのまま本番のリソースを使います。

### Step 4: 公開したアプリを Claude Code で検証する

公開できたら、本当に動くかを確かめます。公開 URL を Claude Code に操作させて、完成条件（メモを貼る→要約が出る→保存・一覧・検索）を満たすかを検証します。ここで、ブラウザを操作する Playwright の MCP を接続します（Claude Code の外のターミナルで実行。コマンドやパッケージ名は変わることがあるので、2026年6月時点のものです）。

```bash
claude mcp add playwright npx @playwright/mcp@latest
```

接続したら、Claude Code に検証を頼みます（「Playwright」と明示すると、ブラウザ操作の MCP が使われます）。

```text
Playwright で、公開 URL（自分のアプリの URL）を開いて、会議メモを1件貼り付けて整形し、要約・決定事項・ToDo が表示されて保存されることを確認して、結果を見せてください。
```

Claude Code が公開 URL のアプリを実際に操作し、メモ投稿から要約表示までが動くかを確かめて報告します。これも「成功を主張させるのではなく、操作の結果（証拠）を示させる」検証です。

!!! warning "注意"
    公開後にうまく動かないとき（要約が出ない、保存されないなど）は、ローカルでは動いていたかを思い出し、「ローカルでは動くが公開すると動かない」ことを Claude Code に伝えて原因を調べてもらいます。多くは本番のデータベース反映（Step 2）やバインディングの設定の差なので、期待と実際を具体的に伝えると切り分けが速くなります。

## まとめ

- 公開前に変更を Git で記録する。秘密の値は `.gitignore` と（必要なら）`wrangler secret put` で分け、Git にも AI にも渡さない
- 本番データベース（remote D1）に `--remote` でテーブルを反映し、`npm run deploy` で Cloudflare に公開して公開 URL を得る
- 本番への反映と公開は取り返しのつかない操作なので、auto モードでも確認を求められる。承認しながら進めるのが安全策になる
- 公開後は Playwright の MCP で実際に操作させ、結果という証拠で動作を検証する
